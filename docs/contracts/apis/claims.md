# Organizer Claims API Contract

## Purpose and Scope

This contract defines the governed interface for the organizer claim workflow. When a CFP is submitted by a community member who is **not** the event organizer (`organizerIsSubmitter = false`), the listing is published as "Unverified — Awaiting Organizer Claim." The claim flow allows the legitimate event organizer to assert ownership, verify their identity via email token, and have the listing status upgraded to "Organizer Verified."

Covered endpoints:

- `POST /v1/claims/{cfpId}` — Initiate an organizer claim for an unverified listing
- `POST /v1/claims/{cfpId}/verify` — Complete claim verification with a token from email

An admin-assisted fallback is also available at `POST /v1/admin/claims/{cfpId}/assign` (see `admin.md`).

These endpoints are served directly by `CfpCompass.Api` and are **not** exposed through APIM. The initiation endpoint requires an authenticated speaker session. The verification endpoint is token-authenticated (single-use, 7-day JWT in the email link).

Out of scope: admin claim management (`admin.md`), submission moderation, and the submission workflow that triggers the claim invitation (`submissions.md`).

---

## API Responsibilities

- Accept a claim initiation request from an authenticated speaker who wishes to claim ownership of an unverified CFP listing.
- Validate that the target CFP is in `UnverifiedAwaitingClaim` status before initiating a claim.
- Prevent duplicate active claims from the same user for the same CFP.
- Publish an `organizer-claim-requested` event to the `organizer-claims` Service Bus topic, triggering the claim invitation email and status update.
- Accept a claim verification request with a valid single-use 7-day JWT token delivered in the invitation email.
- On successful verification, update the CFP record to `OrganizerVerified` status and invalidate the relevant APIM and Redis caches.
- Enforce one active claim per CFP at a time (preventing claim conflicts).

The API does **not** directly modify the CFP record at claim initiation — that is the responsibility of the downstream `CacheInvalidationProcessor`. Email sending is the responsibility of the `NotificationProcessor`.

## Request Model

### `POST /v1/claims/{cfpId}`

| Parameter | Type | Required | Description |
|-----------|------|:--------:|-------------|
| `cfpId`   | UUID | ✔️       | Path parameter. The ID of the CFP to claim. Must be in `UnverifiedAwaitingClaim` status. |

No request body. The authenticated user's identity is taken from the session cookie.

### `POST /v1/claims/{cfpId}/verify`

| Parameter | Type   | Required | Description |
|-----------|--------|:--------:|-------------|
| `cfpId`   | UUID   | ✔️       | Path parameter. The ID of the CFP being claimed. |
| `token`   | string | ✔️       | Query parameter. Single-use 7-day JWT verification token from the claim invitation email. |

No request body.

---

## Field Semantics and Constraints

- **Claim initiation** (`POST /v1/claims/{cfpId}`): Only CFPs in `UnverifiedAwaitingClaim` status can be claimed. Attempting to claim a CFP in any other status returns `409 Conflict`.
- **Verification token**: A signed JWT (`Jwt-SigningKey` from Key Vault). Contains the `cfpId`, `claimantUserId`, and expiry. Valid for 7 days. Single-use — once the verification request is processed, the token is invalidated.
- **One active claim per CFP**: If a claim is already `Pending` for a CFP, a second initiation request returns `409 Conflict` with `{ "error": "claim_already_pending" }`. This prevents multiple organizers from simultaneously claiming the same listing.
- **`verificationToken`** in the Service Bus event is the signed JWT that will be embedded in the claim invitation email link. The token is generated by the API at claim initiation time and included in the event payload so the `NotificationProcessor` can construct the email link without additional lookups.

## Naming and Validation Rules

- `cfpId` is a UUID path parameter, case-insensitive in parsing, normalized to lowercase UUID format.
- `token` is passed as a query parameter `?token=` to match the email link pattern.
- Field names in all JSON responses use `camelCase`.

---

## Request Validation and Governance Rules

- `POST /v1/claims/{cfpId}` requires an authenticated session cookie. Unauthenticated requests return `401 Unauthorized`.
- The target CFP must be in `UnverifiedAwaitingClaim` status. Any other status returns `409 Conflict`.
- If the authenticated user already has an active (Pending) claim for the same CFP, the request is idempotent — a `200 OK` is returned indicating a claim is already in progress for this user and CFP combination.
- `POST /v1/claims/{cfpId}/verify` validates token signature, expiry, and single-use state before updating the CFP status.
- An expired token returns `401 Unauthorized` with `{ "error": "token_expired" }`.
- An already-used token returns `401 Unauthorized` with `{ "error": "token_used" }`.
- A token for a different `cfpId` than the path parameter returns `400 Bad Request`.

## Execution Semantics

### Claim Initiation

1. Authentication middleware validates the session cookie.
2. The API validates the target CFP exists and is in `UnverifiedAwaitingClaim` status.
3. The API checks for an existing active claim from the same user for the same CFP.
4. A `verificationToken` JWT is generated (7-day expiry, signed with `Jwt-SigningKey`).
5. A `ClaimRequest` record is created in Azure SQL with status `Pending`.
6. An `organizer-claim-requested` event is published to the `organizer-claims` Service Bus topic.
7. `202 Accepted` is returned.
8. `CacheInvalidationProcessor` updates the CFP listing status display to "Organizer Claim Pending."
9. `NotificationProcessor` sends the claim invitation email to the CFP's `contactEmail` with the verification link.

### Claim Verification

1. The verifier clicks the email link, which navigates to the `ClaimCfp.razor` page.
2. The page calls `POST /v1/claims/{cfpId}/verify?token={token}`.
3. The API validates the token (signature, expiry, single-use, cfpId match).
4. The `ClaimRequest` record is updated to `Verified`.
5. The CFP record status is updated to `OrganizerVerified` directly in Azure SQL (synchronous write — verification is a terminal state change that must be immediately consistent).
6. Cache invalidation is triggered (APIM cache purge + Redis DEL for the affected CFP).
7. `200 OK` is returned.

## Claim Status Lifecycle

```
UnverifiedAwaitingClaim
        │
        ▼ (POST /v1/claims/{cfpId})
  OrganizerClaimPending
        │
        ├─ (POST /v1/claims/{cfpId}/verify — token verified)
        │         │
        │         ▼
        │  OrganizerVerified
        │
        └─ (POST /v1/admin/claims/{cfpId}/assign — admin action)
                  │
                  ▼
           OrganizerVerified
```

## Status and Observability

Claim initiation follows the async pattern (`202 Accepted`). Claim verification is synchronous (`200 OK`).

All claim events (initiation, verification, admin assignment) are logged to the `AuditLog` table in Azure SQL and to Azure Log Analytics with `cfpId`, `claimantUserId`, and `action` as structured fields.

---

## Error Handling

| HTTP Status | Condition |
|-------------|-----------|
| `400 Bad Request` | Token's embedded `cfpId` does not match the path parameter. |
| `401 Unauthorized` | Missing or invalid session cookie (initiation); expired or already-used token (verification). |
| `404 Not Found` | CFP with the specified `cfpId` does not exist. |
| `409 Conflict` | CFP is not in `UnverifiedAwaitingClaim` status; or an active claim already exists for this CFP. |
| `500 Internal Server Error` | Unhandled exception. Correlation ID included. |

## Security and Access Control

### Authentication

- `POST /v1/claims/{cfpId}`: Requires a valid authenticated session cookie (ASP.NET Core Identity).
- `POST /v1/claims/{cfpId}/verify`: Token-authenticated. Single-use 7-day JWT delivered via email. No session cookie required for verification.

### Authorization

- Any authenticated speaker may initiate a claim for an unverified listing. There is no pre-screening of whether the claimant is the legitimate organizer — the email verification step is the trust mechanism.
- The verification token is sent to the CFP's `contactEmail` (the organizer's address provided at submission time). Only someone with access to that inbox can complete verification.
- Admin-assisted claim assignment (`POST /v1/admin/claims/{cfpId}/assign`) is available when the organizer cannot receive the verification email. See `admin.md`.

### Consumer Identity Trust Model

The claim verification flow relies on email-based proof of inbox access as the identity assertion. The `contactEmail` provided at submission time is the trust anchor. If the email was incorrect or the organizer no longer controls that address, the admin-assisted assignment path provides a resolution mechanism.

## Notes and Comments

- The 7-day verification window is intentionally longer than the 72-hour edit token. Organizers may not monitor the `contactEmail` daily — a longer window improves conversion without meaningfully increasing risk, since the verification only grants ownership of the specific CFP listing (not system-wide access).
- If the verification token expires before the organizer acts, they must contact the admin for assistance via the admin-assisted path. There is no self-service token resend mechanism in the MVP.
- The `claimantUserId` in the `organizer-claim-requested` event payload refers to the authenticated speaker who initiated the claim, not necessarily the organizer. In most cases the claimant is the organizer creating an account specifically to claim their listing.
